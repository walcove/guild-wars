# Optional Solana ownership linking

The address proof binds the configured domain, existing Telegram web session, address, five-minute nonce, explicit purpose and exact message bytes. Standardized offchain v1 is preferred when the wallet advertises it; the supported raw message feature is the fallback. The canonical v1 preamble requires exactly the selected signer. The server verifies Ed25519 with Kit; it never imports a browser signer, accepts a transaction proof or treats the link as provider access, unique personhood or trade authority. No private key/seed is requested or stored by the application. Optional wallet code is confined to `/connect/wallet`, with Wallet Standard discovery and walletWithoutSigner; ordinary research/voting/simulation do not load or require it.

Official [Solana message/authentication guidance](https://solana.com/docs/frontend/messages-and-auth), [Next.js/Kit guidance](https://solana.com/docs/frontend/nextjs-solana) and installed pinned package sources were checked. The read client uses `solanaRpcConnection`, which installs no payer or transaction execution capability. Explicit Wallet Standard dependencies pin the already installed compatible versions. A public devnet `getVersion` request actually returned solana-core 4.4.0; no signer, balance lookup, airdrop or funded action was involved.

Three real-PG tests cover both signing formats, exact domain/content/purpose/signer/session, nonce reuse/expiry, cross-identity address exclusivity and no provider account creation. Two component cases cover disconnected/unsupported states and review-before-sign. Three rendered Chromium cases cover 390/1360px recovery plus an original synthetic Wallet Standard signing flow. Its Ed25519 private key stays non-extractable in the test process; only an in-memory test signing callback is exposed to that fixture. No real wallet profile or chain call is used. A hydration mismatch found by this flow now has a failing/passing browser regression: discovery renders a stable server snapshot until hydration.

Full PostgreSQL suite: 72/72; contracts: 16/16. Whole-app verify passed 86 unit cases before the independent cohort-policy increment. Actual native wallet/hardware capability and transaction-version support remain unverified. A message-only fixture advertises no transaction feature; no newest transaction version is assumed. Provider-specific capability verification remains a separate Task 20/21 gate.
