## Pilot-load check

Use a fake external provider and local/test data. Seed five guilds with 100 members and 200 visible clients polling one composed response every ten seconds. Add a background backlog, one slow provider and simultaneous ballot closure. Measure request percentiles, query counts, queue lag, provider call counts and connection caps. Initial targets: ordinary status p95 below 500 ms and vote transaction completion below 1 second, excluding Telegram network time. Record hardware, versions and actual results; adjust targets with evidence before release.

## Critical end-to-end paths

1. New member, no wallet: Telegram invitation → web linking → research → sourced note → proposal → exact Telegram message → vote/change → simulated booking → midweek → honest settled results.
2. Eligible live member: linked provider/wallet as required → current quote → own review and authorization → verified partial/full fill → midweek capability check → actual settlement/claim → matched, private results.
3. Recovery: close the browser after handoff, revoke a credential or delay a callback, reopen, and recover canonical status without a duplicate economic order.
4. Community: register a measurable forecast before its outcome, preserve a miss, rotate independent member award checks, and exercise the appeal without restricting anyone's research participation.

No browser harness authorizes a real funded trade. Sandbox, synthetic, imported authoritative and funded evidence remain separately labeled. Only an appropriately authorized person/provider completes required live financial confirmations.
