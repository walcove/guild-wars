# 0004 · Telegram identity and browser sessions

First visit creates only an anonymous, high-entropy browser session. It grants no guild, research or provider access. Only a verified private-bot interaction and explicit confirmation in the original browser create/sign into a Telegram account. Names and request-supplied user IDs are never proof. Linking a wallet is independent and never required here.

The session and five-minute challenge store SHA-256 token hashes; raw session tokens are confined to HttpOnly, SameSite Lax cookies (Secure and host-prefixed in production). CSRF uses a session-bound hash plus strict Origin checks. The second HttpOnly CSRF cookie lets same-browser tabs recover their existing token through a private/no-store endpoint rather than invalidating each other. Successful link confirmation atomically consumes the challenge, rotates cookies and revokes the old session. A session has 24-hour idle and 7-day absolute limits, checked on the server; logout revokes it. All private responses are no-store.

One current challenge per browser session; restarting changes the nonce and erases old bot proof. A different browser cannot consume proof. Exact internal proposal/version/origin return context is retained; external URLs, arbitrary query payloads and traversal are rejected. Authentication never grants private-guild membership. Missing test-bot configuration is explicitly unavailable and does not fabricate a signed-in user.

Existing Telegram identities sign into their already verified account; accounts never merge. Changing the linked identity requires a session with Telegram proof less than five minutes old (proof of the existing identity), a separate new-identity bot challenge bound to that session, and original-browser confirmation. The server records this purpose, checks identity conflicts and revokes all prior sessions and provider read authorizations atomically. A fresh session for the new identity is then issued. No trade/withdrawal credentials are stored. Provider-link changes must use the same fresh-proof guard and revoke affected credentials; live-provider linking awaits its own gate.

Only the upcoming authenticated Telegram transport calls the bot-proof service. The local integration suite calls it with synthetic identities and does not send messages or request wallet signatures. Native test-bot and rendered browser evidence remain separate gates.
