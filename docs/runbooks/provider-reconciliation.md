# Provider reconciliation and discrepancies

No provider reader is configured. Gate 0, native records, data permissions, provider custody/settlement evidence and explicit release approval remain unavailable. Default jobs fail visibly and retain existing commitments. The new-preparation pause does not purport to close an order or disable future read-only reconciliation of existing funds.

The internal reader fetches outside SQL locks. Import then rechecks exact owner/account, external order relationship, current read-credential hash, instrument, mode, source time and finality. Arbitrary URLs, transaction hashes, screenshots, client balances and readiness flags are not accepted by any import HTTP route. There is no public import route. Live sources require the approved provider/read gate; original synthetic fixtures enter simulation only.

Provider observations and financial revisions are immutable. Ingestion retries cannot add another premium or liability. Stable fill IDs are globally attributed by provider/account; one provider order or position cannot belong to two sleeves. A changed same-revision payload is a discrepancy, never an overwritten fill. Explicit source lineage appends reversal/replacement ledger events. A settled fill correction waits for its matching corrected settlement and coverage records, then applies the complete set atomically. Corrections retain original records and feed later result revisions; they never selectively remove a losing member.

Unknown, partial and pending orders keep internal reservations. The clock, quote expiry, an expired contract, a failed browser request or a cancellation timeout never proves release. Source cancellation without a complete verified fill set stays conservative. Claimable is distinct from settlement; settlement does not imply withdrawal. A withdrawal transfer cannot add the settlement proceeds a second time. Confirmed Solana records remain provisional until finality evidence is recorded. Missing authoritative fill time is unverifiable; delayed ingestion of an actual in-window fill does not itself make it late.

Unresolved provider discrepancies block new allocation on that account. Corrected records must resolve the source issue; owners retain their private record and can use the provider's known application directly. The application cannot claim it prevented an outside trade. Never store or request a trade/withdrawal-enabled API key. Read references and credentials stay out of public/owner display projections.

Worker recovery uses canonical operation IDs and supported Graphile APIs. After independently confirming the exact owned worker process is dead, `WorkerUtils.forceUnlockWorkers` may unlock its recorded worker ID. Never update Graphile's private scheduling tables or unlock a possibly live worker. The financial SIGKILL test kills only its own child after ledger commit, unlocks only that dead worker, and proves replay cannot duplicate premium/liability.

Remaining provider-dependent work: the selected provider's actual correction/void semantics, definitive cancellation/completed fill-set proof, multiple-position fill mapping, any cash-settled product, actual chain finalization, claims/withdrawal authorizations and native outage/settlement samples. Unsupported records remain pending/discrepant; no adapter or financial API is invented to bypass missing documentation. Gate 0 and release cannot pass from these synthetic tests alone.
